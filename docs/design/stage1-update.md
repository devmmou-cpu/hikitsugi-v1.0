# 段 1 更新まわり 設計案

状態：**決定（2026-11-10、本人の判断）**。決まったことは「決定」の節にまとめ、本文もそれに合わせて直した。

## 作るもの
1. 更新で、新しい連絡先と新しい機器を足せるようにする
2. 更新の記録に、名乗った名前に加えて、PC のアカウント名と PC 名を残す

## 合格の条件（本人の指定）
- 架空のオコジョ精工の説明書に、更新で「エゾクロテン電設」を連絡先として足す。続けて「症状を足す」で分電盤まわりの症状ページを作り、その ③ の連絡先にエゾクロテン電設が使われる
- 更新で機器を 1 台足し、「会社の IT」に載る
- 足した文は Verifier の照合を通り、更新する人の確認を経て、PC 用・スマホ用・manual.json の 3 つに反映される
- 更新の記録に、種類（連絡先の追加、機器の追加）、名乗った名前、アカウント名、PC 名が並ぶ
- 既存の検査（退職する本人を連絡先にしない、電話番号の形、パスワード本体の拒否、round の検査）が、足した内容にも効く

## 今の作り（読んで分かったこと）
- 更新は `update-fix`（連絡先、機器、ページ）、`update-add`（症状）、`update-memo` の 3 つの入口。どれも `beginUpdate` が答えを聞き取りの記録（`INT-`、`GAP-000`／`CHK-00`）に足して、回を 1 つ進める
- 連絡先の修正は Writer に連絡先 1 件だけを書かせる（`part: contact`）。機器の修正は共通部分を丸ごと書き直す（`todo: ['common']`）
- 症状を足すときの共通部分は「前の版の連絡先、定期作業、機器は変えません」（`writer.md` 104 行目）。新しいページは、この時点の連絡先の中から ③ を選ぶ
- 連絡先の名前と番号は、Verifier ではなくプログラム（`contactEvidenceProblems`）が根拠と照らす（11/2 の決定）
- **退職する本人の名前は、文（statements）の中でしか調べていない。** 連絡先の `name` が本人でも、今は止まらない。足す連絡先では `name` が直接入るので、ここを塞ぐ必要がある
- **電話番号の形は、製品の側では調べていない。** 調べているのは「根拠にあるか」だけ。架空の形式の検査は、開発用のフック（`scripts/hooks/check-manual-html.mjs`）と `eval/lib/integrity.mjs` にある
- パスワード本体は、記録の前に `appendReviewEntry` が拒否する。新しい入口も `beginUpdate` を通せば同じく効く
- round の検査（`checkRound`）は `restoreFromBundle` と `update-cancel` にある。新しい入口も同じ回の仕組みを使えば効く

## 1. 更新の最初の選択肢
今は「連絡先を直す」「症状を足す」「手順を直す」「後任のメモから取り込む」の 4 つで、AskUserQuestion の上限（4 つ）に当たっている。

### 案 A：「連絡先・機器」にまとめる（推奨）
```
最初の質問：  連絡先・機器 ／ 症状を足す ／ 手順を直す ／ 後任のメモから取り込む
連絡先・機器： 連絡先を直す ／ 連絡先を足す ／ 機器を直す ／ 機器を足す
連絡先を足す： 業者 ／ 社内の相談先
```
- 「症状を足す」「手順を直す」「メモ」の 3 つは今のまま 1 回で選べる。連絡先の修正だけ 1 回増える
- 機器の修正は、今は「手順を直す」の一覧に混ざっている。「連絡先・機器」に移して、「手順を直す」はページだけにする
- 「業者」か「社内の相談先」かは本人に選んでもらい、ID の頭（`VEN-`／`INH-`）はプログラムが決める。AI に選ばせない

### 案 B：動詞で分ける
```
最初の質問： 直す ／ 足す ／ 後任のメモから取り込む
直す：       連絡先 ／ 手順 ／ 機器
足す：       症状 ／ 連絡先 ／ 機器
```
- 形はそろうが、今いちばん使う「症状を足す」「手順を直す」も 2 回になる
- README、動画、テストに出ている今の 4 択の言葉がすべて変わる

### 案 C：自由に書いてもらい、プログラムが振り分ける
- 語の照合で振り分けると外れたときに戻る道が要り、AI に振り分けさせると「画面と流れは AI ではないプログラムが決める」の約束に反する。採らない

**案 A に決定。** よく使う道を変えず、増えるのは連絡先と機器の 1 回だけで済む。最初の質問の「連絡先・機器」には、description に「連絡先と機器を、直すか足す」と書く。

## 2. 根拠と Verifier
- 足す内容は、更新する人の答え 1 件を聞き取りの記録（`INT-`）にして根拠にする。今の更新と同じく `GAP-000`、`CHK-00` を使う。質問の文で種類が分かるようにする
  - 連絡先：「足す連絡先の、名前、電話番号、何の相手か、受付の時間、契約書の控えの場所を教えてください。分からないものは「分からない」と書いてください。」
  - 機器：「足す機器の、名前、置き場所（部屋と、部屋の中の目印）、何に使うか、止まると何が困るか、パスワードを置いてある場所、してはいけないことを教えてください。」
- Writer の書いた文（連絡先の `role`、`hours`、`contract_location`、`what_to_tell`、機器の `name`、`location`、`purpose`、`impact`、`credential_location`、`caution`）は、ふつうの文と同じく Verifier にかける。根拠はこの `INT-`。Verifier の指示文は変えない
- 名前と番号は文ではないので、今の決まりどおりプログラムが照らす。足すときは、**今回の答え**にあることを求める（記録のどこかにあれば通る今の検査より強くする）。足した連絡先が、更新する人の答えから来ていることを確かめるため
- 足す連絡先に、次の検査を足す
  - 名前が退職する本人の名前の形（`nameForms`）に当たれば止める。**足すとき、直すとき、最初に作るときのすべてで効かせる**（本人の決定）。調整用 3 社の通しの出力 36 回分、サンプル、テストの保存データ（888 ファイル、連絡先 1,093 件）で当たりが 0 件であることを、入れる前に確かめた
  - 名前が今の連絡先と同じなら止める（「連絡先を直す」を案内する）
  - 番号は、**明らかに番号でないもの**（数字が 2 つ未満、数字と区切り以外の文字がある。「内線」「代表」は除く）だけを止める。市外局番からの 10 桁（`0X-XXXX-XXXX` の形）以外の見慣れない形（フリーダイヤル、携帯、内線つきなど）は止めず、確認の段階の表示に「この番号でよいですか」を出して、更新する人に確かめてもらう（本人の決定）。形の検査は足すときと直すとき（`checkContact`）だけにし、最初の作成の検査は変えない（評価の条件を変えないため）
- 足す機器には、置き場所に部屋らしい語がなければ警告（今と同じ。止めない）を出す。名前が今の機器と同じなら止める
- 照合で指摘が出たら、今の差し戻しと同じく、その連絡先か機器の 1 件だけを書き直す（最大 2 回）。止まったら `update-cancel` で前の説明書に戻る

## 3. manual.json とスキーマ
- `updates[]` の項目に、任意で `account`（アカウント名）と `host`（PC 名）を足す。必須にはしない
- `updates[].kind` の値に `add_contact`（連絡先の追加）と `add_device`（機器の追加）を足す。`UPDATE_KIND_LABELS` にも足す
- 種類名は「連絡先の変更」「連絡先の追加」「機器の変更」「機器の追加」にそろえる（本人の決定）。機器の修正（`device`）は「手順の修正」から「機器の変更」に変わり、過去の記録の表示も「機器の変更」になる
- `updates[].pages` は、足した連絡先と機器では空の配列（使うページがまだないため。症状を足したときに、そのページの行が付く）
- 連絡先と機器の形（`contacts`、`devices`）は変えない。機器の ID は今の `D1`〜 の続き、連絡先は `VEN-`／`INH-` の続きをプログラムが振る
- Writer の形（`writerFormat`）に `device`（機器 1 件と、その文だけ）を足す。`contact` は今の形を使う
- `mergeRewritten` で、前の版にない連絡先と機器を末尾に足せるようにする。ほかの文の ID と文面は変えない
- **前の版を読めること：** `account`、`host` のない `updates` も、そのまま通る。表示は名乗った名前だけなので、変わらない。bundle の `schema_version` は 1 のまま（足すのは任意の項目だけ）
- **逆は読めない：** 新しい版で更新した manual.json を古い版のプラグインで開くと、`updates` の項目が増えているので形の検査で止まる（壊れはしない）。README の更新の段落に 1 行書く

## 5. アカウント名と PC 名
### 取り方
- `update-start` のときに、プラグインのプログラムが `os.userInfo().username` と `os.hostname()` を読む。AI にも本人にも入力させない
- `state.json` に残し、`finishUpdate` で `updates[]` の行に入れる。名乗った名前（`by`）と並べる
- `update-start` の表示に「記録します：アカウント名 〈値〉、PC 名 〈値〉」を出し、本人が何が残るかを分かるようにする
- 取れなかったとき（空や例外）は「取得できませんでした」と記録し、止めない

### 画面に出すか
| 案 | 内容 | 良い点 | 弱い点 |
|---|---|---|---|
| **甲（推奨）** | manual.json にだけ残す。画面（PC 用、印刷、スマホ用）には出さない。`hikitsugi history` で端末に一覧を出す | 後任の画面と印刷にアカウント名が載らない。スクリーンショットやサンプルにも入る道がない | manual.json を開かないと見えない |
| 乙 | 「はじめに」の更新の記録の表に、PC 名だけを出す | 誰の PC で直したかが画面で分かる | PC 名は調査データにもあるが、印刷物に載る。表の列が増える |
| 丙 | 両方を表に出す | すべて画面で追える | アカウント名は会社のアカウントのことがあり、印刷と全社の OneDrive に載る |

**甲に決定。** 記録は「あとで追うため」のもので、後任が困って開く画面に要るものではないため。manual.json も OneDrive に置くので、見ようと思えば社内の人は見られる、ということは README に書く。

### 更新を始めたときの表示（本人の決定で足す）
- `update-start` は、直近の更新の記録（日付、名乗った名前、アカウント名、PC 名）を表示する。記録がなければ「更新の記録はまだありません」
- 今回名乗った名前が、過去の記録で別のアカウント名と組になっていたら、「注意：」の行を出す。スキルは、続けるかを AskUserQuestion で聞く（「続ける」「やめる」）。プログラムは止めない
- アカウント名の欄がない前の版の記録とは比べない（注意を出さない）。今回のアカウント名が取れなかったときも比べない

### 実際の値がリポジトリに入らない仕組み
- 取る場所を 1 つの関数（`plugin/lib/identity.mjs`）にまとめる。環境変数 `HIKITSUGI_IDENTITY`（例：`{"account":"user-a","host":"OKJ-PC01"}`）があれば、その値を使い、記録に `identity_source: "env"` を残す
- テスト、サンプルの作り直し、撮影プログラムは、必ずこの環境変数で架空の値を渡す。PC 名は会社の決まり（オコジョ精工なら `OKJ-`）、アカウント名は `user-a` のような意味のない形にする
- 画面に出さない（甲）ので、撮影したスクリーンショットには作りの上で入らない。render のテストで、架空の値が HTML、印刷、スマホ用のどれにも出ないことを確かめる
- `check-secrets.mjs` に点検を足す：実行した PC の `os.userInfo().username` と `os.hostname()`（`.local` などを外した形）を、その場で読み、追跡ファイル、コミット履歴の追加行、作業中の変更、`--files` の書き出したファイルに**語として**出てこないかを調べる。値はリポジトリにも出力にも書かない（「アカウント名の形があります」とだけ出す）
  - 語として、は前後が英数字でないこと。今の README の `devmmou-cpu` のような、別の語の一部には当たらない
  - 3 字未満の名前と、`user`、`admin` のようなよくある名前は調べず、調べなかったことを表示する
  - 画像（PNG、PDF）の中の文字は調べられない。画像は架空の値だけで作る、で守る

### 本人確認ではないこと
これは**記録で、本人確認ではない。** 偽れる範囲は次のとおりで、README と更新の案内に書く。
- 名乗った名前は、誰でも何でも書ける
- アカウント名と PC 名は、ほかの人の PC で開けばその人のものになり、ローカルのアカウントは好きな名前で作れる。環境変数でも変えられる（その場合は `identity_source` に残る）
- manual.json は OneDrive の編集権がある人なら書き換えられる。記録ごと消すことも、書き足すこともできる
- 誰が書き換えたかをより確かに追うなら、OneDrive の版の履歴（会社のアカウントで残る）を見る

## 7. 調整用 3 社で評価をやり直すか
- Verifier の指示文は変えないので、Verifier の評価はやり直さない
- Writer の指示文は、更新の節だけを変える。評価（`eval/run.mjs`）には更新の対象がないので、点数への影響を直接は測れない。最初の作成で使う部分の文面は変えない
- **推奨：段 1 ではやり直さない。** v1.0 の最後に、ほかの段の変更とまとめて調整用 3 社の通しを 1 回行う。見積もりは 11/4 の実績（$2.60＋$2.59＋$1.99）から **約 $7.2**。$5 を超えるので、そのときに改めて承認を受ける。holdout はそのあとに 1 回だけ
- 合格の条件の確認は、架空のオコジョ精工のサンプルを使い、Claude Code のプラグインの流れで 1 回通す（API キーは使わない）

## 8. 作業の分け方（コミットの単位）
1. 記録：`identity.mjs`、`updates[]` の `account`、`host`、`identity_source`、`finishUpdate` で残す、`hikitsugi history`、画面に出ないことのテスト

3. 連絡先を足す：`update-add-contact`、Writer の task、`checkContact` の強化（今回の答え、退職する本人、番号の形、重複）、`mergeRewritten` の追加、テスト
4. 機器を足す：`update-add-device`、`writerFormat('device')`、機器 1 件の検査、テスト
5. 選択肢と指示文：SKILL の案 A、`writer.md` の 3 か所、既存テストの文字列
6. 通しの確認と記録：架空のオコジョ精工で 連絡先 → 症状 → 機器 を通し、`docs/design.md` の決定事項、README の更新の段落（偽れる範囲、古い版で開けないこと）

## やらないこと
- 連絡先と機器の削除、定期作業の追加
- 機器の修正を共通部分の書き直しから `part: device` に移すこと（段 1 では足すときだけ。直すときは今のまま）
- 本人確認（ログインや署名）。アカウント名と PC 名は記録だけ
- アカウント名を画面に出すこと（甲を採る場合）
- 古い版のプラグインで、新しい manual.json を開けるようにすること
- 評価セット（`eval/sets`）と正解データの変更、holdout の実行
- README の「模擬評価」「実在の会社では未検証」の但し書きの変更
- 実在の会社での検証

## 決定（2026-11-10、本人の判断）
1. 最初の選択肢は案 A
2. 更新の記録の種類名は「連絡先の追加」「機器の変更」「機器の追加」（既存の「連絡先の変更」とそろえる）
3. アカウント名と PC 名は甲（manual.json にだけ残し、PC 用・印刷・スマホ用の画面には出さない）。更新を始めたときに直近の記録を出し、名前とアカウント名の組が過去と違えば注意を出して続けるかを聞く（止めない）。欄のない前の版では注意を出さない
4. 連絡先の name が退職する本人なら、足すとき、直すとき、最初に作るときのすべてで止める
5. 電話番号は、明らかに番号でないものだけ止める。見慣れない形は止めずに「この番号でよいですか」と確認を求める
6. テスト、サンプル、撮影は、環境変数で架空のアカウント名と PC 名を渡す。check-secrets に、実行した PC のアカウント名と PC 名の点検を足す
