## 2. 縮める案
### 案 A（推す）：手順ページを、3 枚ずつ同時に書く
- 共通部分を書き終えたあと（ページの一覧が決まったあと）、手順ページの Writer を **3 つまで同時に** 起こす。主のエージェントは、1 つの返事の中で Agent を 3 つ呼ぶ
- 今は Writer への指示が 1 つのファイル（`writer-task.json`、`writer-format.json`）なので、同時に書けない。ページごとのファイル（`writer-task-<回>-<部分>.json`）に分ける（プログラムの変更）
- 検査（`check-writer`）は、書き終えたページから 1 つずつ行う。検査の中身と、問題があれば Writer に直させる流れは今のまま
- **枠に当たったら順番に戻す：** Writer の 1 つが、利用の上限や混雑のエラーで失敗したら、残りは今と同じ 1 枚ずつに戻す。戻したことを本人に 1 行で伝える
- 差し戻しの回（2 回目以降）の書き直しも、同じく 3 つまで

**見込み：** 手順ページ 12〜16 枚で、今 約 8〜11 分 → 約 3〜4 分。**1 社 約 5〜7 分短くなる**（全体の約 1 割）。

### 案 B（小さい）：言い方の索引と、手順の絵の並べ方を同時に
- どちらも Verifier の合格のあとに 1 回ずつ呼び、互いの結果を使わない。同時に起こす
- **見込み：** 約 30 秒〜1 分

### この案でしないこと
- Verifier を分けて同時に動かすこと（照らす単位が変わり、誤り検出に影響しうる）
- 指示文、モデル、検査の基準を変えること
- 聞き取りを速めること（次の問いは前の答えで決まる）

## 3. 危なさ
| 危なさ | 中身 | 手当て |
|---|---|---|
| 契約の枠 | Pro の契約では、同時に起こすと、短い時間に使う量が増え、利用の上限や混雑のエラーに当たるおそれがある。使う量の合計は変わらない | 同時は 3 つまで。エラーが出たら順番に戻す。Max と API キーでは当たりにくいと見込むが、確かめていない |
| 画面の見え方 | 3 つの Writer が同時に動き、表示が混ざる | 進み具合の行（「15 枚中 4 枚」）は検査の出力から出すので、順番は変わらない |
| 検査の取り違え | 同時に書いたページのファイルを、別のページとして検査する | ページごとのファイル名に分け、検査はページの ID で行う。テストで確かめる |
| 精度 | 担当の指示文は同じで、1 回に 1 ページを書くことも同じなので、変わらない見込み | 前と後で、誤り検出、誤検出、根拠のない記載を測る |
