# 設計案：自由な項目と引き継ぎ

状態：**済み（11/15）**。決定は 11/14（本人が推奨をすべて了承。予算 $30 を承認）。v1.0 の順番 3。結果は `docs/eval-results.md`。11/14 に本人の要望を受けて Claude が書いた。決まったことは §11 にまとめた。

この段は 4 つのことからなる。
1. 枠の外を自由に足す段（20 問と定番の症状のあと）
2. 決まった作業（`routines`）を、更新で足す・直す
3. 担当を引き継ぐ操作
4. ホスト名とログイン ID の記録と表示（段 1 の決定 3 を変える）

守ること（4 つに共通）：
- 根拠のない記載を作らない。手順は、承認済みの部品と前任者の答えからしか作らない
- 20 問、定番の症状を選ぶ 1 回と追加の質問（決まった部分）は 25 分以内のままにする
- 誤りの検出 10/10、誤検出 0 を保つ。`verifier.md` と正解データは変えない
- 前の版の説明書（`manual.json`）を読める
- 「証明」の語を使わない。アカウント名と PC 名は**記録で、本人確認ではない**

## 1. 枠の外を自由に足す段
### 流れ
20 問、定番の症状を選ぶ 1 回、追加の質問のあと、Writer の前に置く。質問の文は、プログラムが決まった型で作る（Interviewer は使わない。指示文も変えない）。

1. **挙げてもらう（1 問）：** 「ほかに引き継ぐものはありますか。会社の IT と、それにつながる機器やソフトを、1 行に 1 つずつ書いてください（例：工場の機械につながる PC、レジ、業務ソフト）。経理の締めのような業務の手順は、この説明書の対象外です。なければ「ない」と書いてください。」
   - 行ごとにプログラムが分ける（AI に分けさせない）。6 行目からは「まだ聞いていない項目」に残す
2. **種類を選んでもらう（1 件に 1 回、AskUserQuestion）：** 「機器・ソフト」「相手（連絡先）」「決まった作業」「IT ではない（載せない）」の 4 つ
3. **中身を聞く（1 件に 1 問）：** 種類ごとに決まった型で、まとめて聞く。分からないものは「分からない」と書いてもらう。パスワードは保管場所だけを聞く
   - 機器・ソフト：置き場所（ソフトなら入っている PC）、何に使うか、止まるとどうなるか、困ったときの相手、パスワードを置いてある場所、してはいけないこと、止まったときに前任者がしていたこと
   - 相手（連絡先）：段 1 の「連絡先を足す」と同じ問い（業者か社内かは、そのあと AskUserQuestion で聞く）
   - 決まった作業：何を、どのくらいの間隔で、どうやって、終わったことを何で確かめるか（§2 と同じ型）
4. どの問いにも「ここまでにする」を選べる。残った項目は、`state.json` と説明書の「まだ分かっていないこと」に「挙がったが、まだ聞いていないもの」として題名を並べる。更新を始めたとき（`update-start`）に件数を出し、更新の「機器・ソフトを足す」「連絡先を足す」「決まった作業を足す」で足せることを伝える

### 載せ方
| 種類 | 載せる先 | 根拠と検査 |
|---|---|---|
| 機器・ソフト | 機器の一覧（`devices`）に 1 件。止まったときの答えがあれば、症状のページを 1 つ（題名は「〈名前〉が止まった・動かない」の型） | 根拠はその項目の答え（`INT-`）だけ。調査（`INV-`）と部品（`LIB-`）は使わない。困ったときの相手が今の連絡先にいなければ、答えに名前と番号がある場合だけ連絡先も足す（段 1 の検査をそのまま使う） |
| 相手（連絡先） | 連絡先に 1 件 | 段 1 の「連絡先を足す」と同じ検査（今回の答えにある、退職する人でない、番号の形、重複） |
| 決まった作業 | `routines` に 1 件 | §2 と同じ |
| IT ではない | 載せない | 題名だけを、はじめにの「この説明書の対象外として挙がったもの」に並べ、「引き継ぎ先は社長に確かめてください」と添える（推奨。答えの言葉を使うので根拠がある） |

- **部品のない物に手順を作らない：** 自由な項目の症状のページは、手順の欄に部品を置かない。前任者が答えた言葉の手順だけを置ける。判定は「確認してから」「業者へ連絡」「社内で相談」のどれかで、「自分で直せる」は使わない（推奨。部品の確かめがない物を、後任が一人で操作する形にしないため）。手順の答えがなければ、③ の連絡先だけのページになる
- プログラムの検査：自由な項目から作った文の根拠が、その項目の `INT-` だけであること。症状のページに `LIB-` がないこと。判定が「自分で直せる」でないこと。どれも Verifier の前に止める
- **範囲：** 会社の IT と、それにつながる機器・ソフトの一次受け。境目の例を、挙げてもらう問いと README に書く（「会計ソフトが開かない」は対象。「会計ソフトでの月の締めの手順」は対象外）。種類で「IT ではない」を選んでもらうのが基本。AI に対象外を判定させない

### 上限と時間
- 上限：**5 件**（推奨）。1 件あたり、種類の選択 約 0.3 分＋中身の 1 問 約 1.5 分
- 時間：挙げてもらう 1 問 約 1 分＋5 件で約 9 分。合わせて**約 10 分まで**。決まった部分（ページの質のあとで約 24.9 分）とは別に数え、始める前に「ここからは任意です。途中でやめて、あとで更新で足せます」と伝える
- ページは最大 5 つ増える。Writer と Verifier の費用は 1 社あたり約 +$0.3〜0.8 の見積もり

### 必須 40 項目と調査スクリプト
- **変えない：** 40 項目、空白の見つけ方（gap-finder）、調査スクリプトは変えない。自由な項目は 40 項目の網羅に数えない（別に「自由な項目の件数」として出す）
- 40 項目のうち、Windows の事務所を前提にするのは CHK-31（Windows Update の運用）と、調査で埋める項目。工場の PC、レジ、業務ソフトのような業種特有の物は、40 項目の外なので、この段で受ける。調査していない機器は、そのページの「もとにした情報」が「聞き取り」だけになる（今の表示のまま）
- **この段でも受けられないもの：** Mac だけの事務所や、調査スクリプトを動かせない会社。調査の仕組みを変える必要があり、この段の範囲の外とする（README の限界に書く）

## 2. 決まった作業を、更新で足す・直す
### 選択肢の並び（1 回の質問は 4 つまで）
**案 B（推奨）：よく使う 2 つを今のまま 1 回で選べるようにする**
```
最初の質問：     連絡先・機器・作業 ／ 症状を足す ／ 手順を直す ／ メモ・担当の引き継ぎ
連絡先・機器・作業：直す（一覧から選ぶ） ／ 連絡先を足す ／ 機器・ソフトを足す ／ 決まった作業を足す
  連絡先を足す：   業者 ／ 社内の相談先
メモ・担当の引き継ぎ：後任のメモから取り込む ／ 担当を引き継ぐ
```
| 操作 | 今の回数 | 案 B |
|---|---|---|
| 症状を足す、手順を直す | 1 | 1（変わらない） |
| 連絡先・機器を直す | 2＋一覧 | 2＋一覧（一覧に決まった作業も並ぶ） |
| 連絡先を足す | 3 | 3 |
| 機器を足す | 2 | 2 |
| 決まった作業を足す・直す | なし | 2（直すは＋一覧） |
| 後任のメモから取り込む | 1 | **2（1 回増える）** |
| 担当を引き継ぐ | なし | 2 |

**案 A：動詞で分ける**
```
最初の質問：直す（一覧から選ぶ） ／ 足す ／ 後任のメモから取り込む ／ 担当を引き継ぐ
足す：      症状 ／ 連絡先 ／ 機器・ソフト ／ 決まった作業
```
- 形はそろい、連絡先を直すのは 1 回減る。今いちばん使う「症状を足す」が 2 回になり、README、動画、テストの言葉が変わる（段 1 で動詞で分ける案を採らなかった理由と同じ）

- 案 B では、「直す」の一覧に連絡先、機器、決まった作業を並べ、ページは今のまま「手順を直す」で選ぶ。「機器を足す」は「機器・ソフトを足す」に名前を変える（業務ソフトも機器の一覧に載るため）
- 更新を始めたとき、名乗った名前が今の担当と違えば、「担当が代わったなら『メモ・担当の引き継ぎ』の『担当を引き継ぐ』を選んでください」の行を出す（止めない）

### 足す・直す
- 足す問い：「足す作業の、名前、間隔（毎週・毎月・毎年。毎年なら何月）、やり方、終わったことを何で確かめるか、だれがしているかを教えてください。」間隔は AskUserQuestion で「毎週」「毎月」「毎年」「決まった間隔ではない」から選ぶ。「決まった間隔ではない」なら、作業にせず「症状を足す」か「手順を直す」を案内する
- `frequency` の値は今の 3 つのまま（スキーマを変えない）。3 か月ごとのような間隔は、題名の文に書く
- Writer に `part: routine`（作業 1 件と、その文だけ）を足す。ほかの作業の ID と文面は変えない。ID は今の続きをプログラムが振る
- 手順に部品（`LIB-`）を使うときは、今の作成と同じ検査を通す（順番 1 の「向きのある部品」の検査も効く）
- 記録の種類：`routine`「決まった作業の変更」、`add_routine`「決まった作業の追加」
- スマホ用の束には、今と同じく決まった作業を出さない（PC 用と `manual.json` に出る）

## 3. 担当を引き継ぐ操作
### 聞くこと
- 「去る人」：今の担当（記録がなければ、説明書を作った前任者）を候補として出し、AskUserQuestion で「〈名前〉さん」「別の人」から選んでもらう
- 「新しい担当」：名前を書いてもらう。名乗った名前（`update-start`）と同じでなくてよい
- 引き継ぐ日：今日の日付（プログラムが入れる）

### 去る人が残っていないかの検査
- 退職した人の一覧を、`retiree`（最初の前任者）と、引き継ぎの記録の「去る人」すべてから作る。今の `nameForms` による検査（連絡先の `name`、文の中で連絡先・相談先にしている書き方、行き止まりの答え）を、一覧の全員に効かせる。**作成、更新、引き継ぎのどの段でも**効く
- 引き継ぎの操作では、次の 2 つに分けて見せる
  - **(a) 直すまで完了しないもの：** 去る人を連絡先（`contacts[].name`）、連絡・相談・転送の相手、パスワードの保管場所（`credential_location`、`caution`）、決まった作業をする人にしている文と項目
  - **(b) 1 件ずつ確かめるもの：** 去る人の名前が出てくるそのほかの文（「田中さんが設定した」など、経緯の説明）。「このままでよい」か「直す」を選んでもらう
- (a) は、今の「連絡先を直す」「手順を直す」と同じ道で 1 件ずつ直す（Writer、Verifier、確認）。(a) が 0 件になり、(b) をすべて選び終えるまで、引き継ぎの記録を付けない。途中でやめたら、次に更新を始めたときに「引き継ぎの途中です。残り n 件」を出す
- `updates[].by` と `review.reviewer`（誰が確認したかの記録）は直す対象にしない

### 記録と表示
- bundle に `handovers[]`（`from`、`to`、`date`、アカウント名、PC 名、ドメイン、`identity_source`、要約値）を足す。`retiree` は今のまま残す（前の版との互換）
- 更新の記録の表に、種類「担当の引き継ぎ」、内容「佐藤さん → 社長」の形の行を出す
- はじめに：今の「前任の〇〇さんが全ページを確認したもの」は、作った時の記録なので残す。その下に「今の担当：〇〇さん（〇年〇月〇日から）」を出す。引き継ぎの記録がなければ出さない（作成のときに後任の名前を聞かない。決まった部分の問いを増やさないため）
- 角印は今のまま（最新の確認者）。各ページの「作成：」の行も今のまま
- **退職後に聞く道（ページの質の段で入れる）との関係：** 社長を通して前任者に聞く道は、はじめにの別の欄（`after_leaving`）の 1 文だけで、連絡先（`contacts`）と ③ には入らない。退職した人の検査は、この欄だけを除いて、引き継ぎで足した去る人にも効かせる。引き継ぎのとき、`after_leaving` に去る人が書かれていれば、(b) の 1 件ずつ確かめるものとして見せる

### 評価とテストの人物
- 使える人物名は、田中さん、佐藤さん、社長だけ。引き継ぎの通しは「佐藤さん（今の担当）→ 社長」で組み、佐藤さんを社内の相談先にした説明書から始める。3 人目の担当の名前が要るなら、名前の許可リストに足すかを本人が決める（今は足さない）

## 4. ホスト名とログイン ID の記録と表示
### 記録すること
- **最初に作るとき：** 前任者が全ページを確認したとき（`markReviewed`）に、`review` に `account`、`domain`、`host`、`identity_source` を残す。作成の印と同じ時点の記録にする
- **更新と引き継ぎのとき：** 今の `account`、`host`、`identity_source` に `domain` を足す
- ドメイン名は、Windows では環境変数 `USERDOMAIN` から読む（Node.js に取り出す関数がないため。外のコマンドは動かさない）。Microsoft Entra ID に参加した PC では `AzureAD`、ローカルのアカウントでは PC 名と同じ値になる。Windows でなければ記録しない（「なし」）
- 取れなかったときは「取得できませんでした」と記録し、止めない（今と同じ）

### 表示（段 1 の決定 3 を変える）
| 出す場所 | 案（推奨） |
|---|---|
| PC 用の「はじめに」の更新の記録の表 | 列「記録した PC」を足し、「ドメイン\アカウント名 ／ PC 名」を出す。一番古い行に「作成」の行（`review` の記録）を足す |
| 印刷 | PC 用と同じ（はじめには印刷に出る） |
| 作成の印 | はじめにの「前任の〇〇さんが全ページを確認したもの」の下に、「作成の記録：日付、名前、アカウント名、PC 名」の 1 行。角印と各ページの「作成：」の行には出さない（14 ページすべてに同じ値が並び、角印は 64px で入らないため） |
| スマホ用の束 | **出さない（推奨）** |
| `hikitsugi history`、`update-start` | 今と同じく出す。ドメインを足す |

- 表のそばに「アカウント名と PC 名は、その操作をした PC から自動で取った記録です。本人確認ではありません。」と出す。`identity_source` が `env` の行は「（指定した値）」と添える
- **スマホ用の扱い：**
  - 甲（推奨）：出さない。スマホ用の束は、社員の前で開き、画面を見せたりスクリーンショットを送ったりしやすい。後任が社員に答えるのに要らない。今も束に更新の記録の表はない。記録は PC 用、印刷、`manual.json` と OneDrive の版履歴で追える
  - 乙：束に「00_更新の記録」のファイルを足す。スマホしか持たない人も見られるが、アカウント名が束の目次に並ぶ
- 決定の変更は、`docs/design.md` の決定事項と `stage1-update.md` に「段 1 の決定 3 を、11/14 の本人の要望で変えた」と残す

### 偽れる範囲（README と案内に書く）
- 名乗った名前は、誰でも何でも書ける
- アカウント名、ドメイン名、PC 名は、ほかの人の PC で開けばその人のものになる。ローカルのアカウントは好きな名前で作れる。`USERDOMAIN` と `HIKITSUGI_IDENTITY` の環境変数で変えられる（後者は「指定した値」と出る）
- `manual.json` は、置いたフォルダの編集権がある人なら書き換えられる。下の要約値も作り直せる

### 記録の書き換えに気づく仕組み（要約値の鎖）
- 作成の記録、更新の記録、引き継ぎの記録のそれぞれに、**前の記録の要約値**（`prev`：前の記録を決まった順の JSON にした SHA-256 の先頭 16 字）と、**その時点の中身の要約値**（`content`：文、ページ、連絡先、機器、決まった作業）を持たせる。秘密の鍵は使わない
- `update-start` で鎖を確かめる。合わなければ「注意：前の記録か中身が、プラグインの外で変わっています」を出し、続けるかを聞く（止めない。今のアカウント名の注意と同じ扱い）。続けたら、新しい記録に「つながりの切れ」を残す
- はじめにの更新の記録の表の下に、最新の記録の要約値（16 字）を出す。印刷した紙と照らせるようにする
- 要約値のない前の版の記録とは比べない。鎖は、要約値を持つ最初の記録から始まる

| 気づけること | 防げないこと |
|---|---|
| 過去の記録 1 行を書き換えた、消した、並べ替えた（後ろの記録を作り直していないとき） | 鎖ごと作り直すこと（作り方は公開されていて、鍵がない） |
| 前回の更新のあと、プラグインの外で中身（文や連絡先）を書き換えた | 最新の記録を消すこと、古い版の `manual.json` に置き換えること（ファイルだけでは分からない。印刷した紙か OneDrive の版履歴と照らせば分かる） |
| 印刷した紙の要約値と、今のファイルの違い | 嘘の名前で正しい記録を作ること。誰が書き換えたかを知ること |

- 誰が書き換えたかを確かに追う手段は、OneDrive の版履歴（会社のアカウントで、サーバーの側に残る）とする

### OneDrive に置く案内
- README の「使い方」と、作成の最後と更新の最後の案内に、「PC 用、スマホ用のフォルダ、`manual.json` は、会社のアカウントの OneDrive に置いてください。版の履歴に、いつ、誰が変えたかが残ります。手元の PC だけに置かないでください。」を書く
- 版履歴の見方は、Microsoft の手順に任せる（同梱しない）。OneDrive でない置き場所では、版の履歴がある場所を勧めるだけにする

### 実際のアカウント名と PC 名が出ないことの確かめ方
今は「画面に出さない」ので、撮影したものには作りの上で入らない。表示すると、この守りがなくなるので、次で置き換える。
1. **環境変数を必須にする（テスト、サンプル、撮影、評価の道具だけ）：** サンプルの作り直し、撮影、README の画像、`eval/stage1-update.mjs` は、`HIKITSUGI_IDENTITY` がないと動かない（今は「あれば使う」）。テストは共通の準備で必ず架空の値を渡す。**実際に使うとき（`/hikitsugi:start` と `hikitsugi.mjs`）は、今のまま PC から読む。** プラグインの側では環境変数を求めない。使う人が環境変数を置いた場合だけ、その値を使い、記録と表示に「（指定した値）」と出る（11/14 に本人と確認）
2. **値の形の検査：** `samples/` の `manual.json` のすべての記録が `identity_source: env` で、アカウント名が `user-` の形、PC 名が会社の決まり（`OKJ-` など）、ドメインが架空の形であることを、テストで確かめる
3. **書き出すときの照合：** サンプルと撮影のプログラムは、書き出す HTML、印刷、スマホ用の束の文字に、実行した PC のアカウント名、PC 名、`USERDOMAIN` が語として出ないかを、書き出す前に調べる。出たら止め、値は表示しない（「アカウント名の形があります」とだけ出す）
4. **表示のテストを逆にする：** 今の「架空の値が HTML に出ない」テストを、「PC 用と印刷には指定した架空の値が出る。スマホ用には出ない」に変える
5. **check-secrets：** 今の点検（追跡ファイル、履歴の追加行、作業中の変更、`--files`）に `USERDOMAIN` を足す。`WORKGROUP`、`AzureAD` のようなよくある値と 3 字未満は調べず、調べなかったことを表示する
6. 画像の中の文字は調べられない。3 の照合を通った HTML からだけ撮る、で守る
